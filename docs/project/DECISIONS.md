# Decisions

Why ACME Scout is built the way it is. Each entry says what was decided, why, and what it costs.

## Design decisions

| Decision | Why | Trade-off |
|---|---|---|
| Milestones stand in for the email's "deliverables" | The instructor's own term; one entity avoids duplicate data | None noted |
| `DELETE` archives instead of deleting | Meets the email's CRUD requirement and the instructor's "never delete, archive instead" rule | Archived rows stay in the database and must be filtered everywhere |
| One `v1` Lambda with a module per feature | Shared auth, database and validation code without copy-paste; one deploy | One function handles all traffic |
| Pure-Python dependencies only (`pg8000`, `PyJWT`, standard-library PBKDF2) | Packages on Windows without Docker or the Linux VDI | No `psycopg`, `bcrypt` or `pydantic` |
| Vitest and Playwright instead of Jest and Cypress | Vitest works with Vite out of the box; Playwright tests real mobile screens and runs in parallel; the guide says "tools *like*" | Names differ from the guide's examples |
| Passwords: 6+ characters with a digit and a special character; temporary passwords expire after 72 hours; forced change at first login | The owner's rule, hardened against guessing | Users must change their password once |
| Hourly rate = salary ÷ 2,080, copied onto each time entry when it's approved | A documented assumption (52 weeks × 40 hours); salary changes don't rewrite past costs | Ignores benefits and overhead |
| JWT signing secret stored in the `app_secrets` table | Avoids changing the Lambda's environment in Terraform | Read once per cold start |
| Every time entry needs manager approval; 40 hours is a warning with one alert per person-week | The owner's rule: managers control what reaches the budget | Managers have an approval queue to work through |

## Implementation decisions

| Decision | Why | Trade-off |
|---|---|---|
| Records you can't see return `404`, not `403` | Doesn't reveal that a project or person exists | Debugging "why can't I see it" needs the audit log or an admin |
| Planned hours are a **hard** 40 h/week cap; logged hours over 40 are only a **warning** | Planning is a promise the manager controls; real overtime happens and should be visible, not hidden | Two different rules around the same number, so the UI labels them carefully ("planned" vs "logged") |
| The over-40 flag is frozen on each entry when it's saved | Later edits don't rewrite history, and nothing has to be recalculated | Lowering Monday's hours afterwards doesn't clear Friday's flag |
| One alert per person-week, guaranteed by a unique constraint as well as the code | Two saves that race can't produce two alerts | None noted |
| Race-prone steps are single atomic `UPDATE … RETURNING` statements: the lockout counter, reset-code attempts, the refresh-token claim | Two concurrent requests can't both pass a check | Slightly denser SQL |
| Unknown usernames are checked against a dummy password hash | Sign-in takes the same time whether or not the account exists | One wasted hash per bad username |
| The refresh cookie is `HttpOnly`, `SameSite=Strict` and scoped to `Path=/api/v1/auth`; the access token lives in memory | Scripts can't read the cookie, it isn't sent to other endpoints, and cross-site requests can't use it | A page reload makes one refresh call to restore the session |
| When email can't be sent, the admin sees the temporary password **once** | Lets onboarding work despite the VPC having no route to SES | The admin has to pass it on securely |
| Removing someone from a project also removes their milestone assignments there | "Assigned" always implies "on the project"; their logged hours stay on record | The manager has to reassign if they add the person back |
| The local dev server handles one request at a time | Mirrors a single Lambda container and avoids sharing one database connection between threads | Slower than a real server; fine for one developer |
| The e2e suite always starts the API on a fresh `overwatch_e2e` database | Every run sees the same demo data | Each run pays for about 5 s of migrating and seeding |
| Managers see an entry's **cost**, never the person's hourly rate; admins and the person themselves see the rate | A rate × 2,080 is the salary, and only admins may see other people's salaries | Spec §3.7 shows hours and cost, so the rate can still be worked out from cost ÷ hours. Hiding it removes the direct leak, not the arithmetic |
| Approve and reject carry the hours the manager saw, and the `UPDATE` only matches a still-pending entry with those hours (`409 STALE_ENTRY` otherwise) | A manager never approves hours they haven't seen, and two decisions can't both win | The manager reloads and decides again |
| Re-saving a rejected cell unchanged resubmits it (the timesheet's **Resubmit** button) | A wrongly rejected entry can go back for approval without inventing a change | None noted |
| `manager.demo` and `employee.demo` never lock and can't change their password; every other seeded account gets a random password on the live site (`rotate_demo` op) | Their password is published for graders. Lockout or a password change would let one visitor break the demo for everyone, and the other demo accounts shared the same known password | Anyone can sign in as those two demo accounts, as intended. Real accounts keep the normal lockout |
| Status changes go through a dedicated `POST /milestones/{id}/status` | One place enforces who may make which transition | One more endpoint than a generic `PUT` |

## Decisions from the feature build (2026-10-14 and 2026-10-15)

| Decision | Why | Trade-off |
|---|---|---|
| **Messaging follows the chain of command, later relaxed for peers.** At first an employee could only start a conversation with their own manager and the managers (and active delegates) of their live projects. It was relaxed so employees can also message other employees; admins, executives and unrelated managers stay off limits for employees, while admins, executives and managers may message anyone ([`rules/messaging.py`](../../backend/v1/app/rules/messaging.py)) | Keeps conversations with leadership purposeful and stops anyone cold-messaging an executive, while peers on shared milestones need to coordinate without going through a manager | An employee who needs an admin has to go through their manager; the rule is checked on the server for every start, so the screen only offers allowed contacts |
| **One reporting manager per employee** (`users.manager_id`) | One clear line for approvals, reminders, messaging permissions and "my manager" everywhere | Matrix reporting isn't modelled; project managers and delegate approvers cover the cross-team cases |
| **Executive is a read-only role**, enforced centrally in the router: every write is `403 READ_ONLY` unless a route opts in (own account, photo, notifications, messages), and salary and hourly-rate keys are stripped from every response to an executive | Sponsors can see everything without risk; a write route added later is read-only for them by default, and pay can't leak through a new response shape | An executive can't fix anything they spot; they message the owner instead. `test_executive.py` must be updated when a route legitimately opts in |
| **Delegate approver** per project, with an optional end date: one other active manager or admin who may decide that project's hours | Approvals don't stall while a manager is away, without moving the queue or sharing a login | Two people can act on the same queue; stale decisions are refused (`409 STALE_ENTRY`) and each decision is audited "as delegate for" |
| **A public demo admin (`demo.admin`) with a 5-minute session** and a fail-closed write allow list, alongside the private real admin logins | Graders can see the admin experience with a published password, while nobody can lock others out, change credentials or people, or submit to HR; anything not reviewed is refused | Some admin screens show disabled controls in the demo. The session can't be extended by refreshing, so a long demo means signing in again |
| **No live data reset: demo data is improved by additive operations** (`demo_backfill` fills blanks, `demo_curate` adds missing plan steps and archives two test items, dry run first) | What graders and the owner did on the live site stays; a reset would wipe their work and the audit trail | Operations are more complex than a reseed, and must be idempotent (a second run adds nothing) |
| **Department presets**: one six-step milestone plan per department (Technology, Operations, Risk & Compliance) in [`presets.py`](../../backend/v1/app/presets.py), offered as project templates | New projects start consistent, with objectives, done-when checklists, skills, estimates and dependencies, and the demo projects look like real plans | Plans are code, not admin-editable; a fourth department gets no template until one is added |
| **Difficulty, priority and severity are separate and labelled in words, each with its own colour family.** Priority (how urgent: low → critical) is red/amber with a flag or chevron and reads "High Priority"; difficulty (how much it weighs in progress: easy 1, medium 2, hard 3) is a teal ramp with weight dots and reads "Hard Difficulty"; insight severity reads "High Severity". The default Medium priority chip is hidden in compact lists | People read a bare "High" or "Medium" chip as the wrong thing; status, risk, priority and difficulty colours never collide | More text on every chip |
| **HR corrections instead of locking sent hours.** Hours already submitted to HR follow the normal rules: an edit sends them back to pending, flags them "Changed after HR submission", and the next submission re-sends them as a correction with the previous hours | Real mistakes get fixed through the usual approval path; each submission's payroll CSV is a frozen copy, so history never changes | Payroll has to process correction rows; admins watch the **Needs re-submission** list |
| **Managers and admins don't log hours by default**; an admin turns on "Tracks own hours" for those who do | Most managers and admins don't bill time, so empty timesheets, Friday reminders and missing-timesheet entries for them were noise | Someone who should log hours needs the switch turned on first (`403 TIMESHEET_DISABLED` until then) |
| **Hour-tracking safeguards inform, they don't block.** An optional start/stop timer (one at a time, New York day, quarter-hour rounding, stopped lazily at midnight); proof of work on new or changed hours (a 10–500 character note or a same-day progress update; unchanged old hours are grandfathered; a timer stop never fails for want of a note and is flagged instead); red flags shown to approvers only (same hours daily, long day, closed milestone, backdated, over plan, no activity, no proof), with the activity-based flags starting at a go-live time | Approvers get evidence to trust hours without making honest people fight the tool; nothing needs a scheduler (the Lambda has none) | Flags are heuristics and can fire on honest work; the approver decides. One timezone (New York) for everyone, since the app keeps no per-user zone |
| **Stopping a timer keeps a draft; the employee submits it, and timer cells are locked.** The first version added the stopped time straight into that day's entry as pending hours. Now the stop keeps the rounded hours on the timer row as a draft that pre-fills the cell, **Submit** sends it with proof of work like any hours, and the cell can't be typed over (`409 TIMER_HOURS_LOCKED`): a correction is a **Request a change** that the project's manager, delegate or an admin approves or rejects (migration 015) | Timer hours are evidence: if anyone could type over them, "Tracked 100%" would mean nothing. Keeping submission a deliberate step means a forgotten timer never reaches the approval queue on its own, and the employee still adds the note | One more step for the employee (Submit after stopping) and a request round-trip to fix a wrong timer; drafts count nowhere (budget, 40h alert) until submitted |
| **A live feed of running timers, with a remote stop that carries a message.** Managers see their people's running timers tick on **Live now**; managers and admins can stop one, and the reason reaches the person as a bell alert and in their one-to-one thread | A timer left running is the most common timer mistake, and the person who notices is usually the manager. A required message (10–500 characters) means a stop always comes with a reason the employee reads where they already talk | Managers can see when someone is working, which some teams may find intrusive; executives see it read-only, and the public demo admin can't stop anyone (it would message a real person) |
| **Limit thresholds: warn the employee at 100%, alert the approvers at 125%.** Three limits per running timer: the 8h day, the milestone's estimate and the 40h week ([`rules/timer_limits.py`](../../backend/v1/app/rules/timer_limits.py)) | 100% is where the person should notice; a manager only needs to hear about a clear overrun, so a 25% margin keeps the bell quiet for ordinary long days. One alert per timer and limit (a primary key on `time_timer_alerts`) stops repeats | Fixed numbers for everyone: planned hours don't lower the 8h day, and nothing is configurable per team |
| **Lazy evaluation instead of a scheduler.** The midnight auto-stop and the 125% alerts are worked out when someone reads: the person's own timer reads, start and stop, a manager's Live now read, and the notification poll. The employee's 100% warning is computed on screen from the `warn_at`/`over_at` times the server returns | The workshop infrastructure gives one Lambda and no scheduler, and the bell already polls every 30 seconds, so something always reads soon enough | An alert arrives on the next read, not at the exact second; a timer nobody looks at stays "running" in the database until the next read stops it at 23:59:59 of its day, so the recorded hours are still right |
| **Puppy creates several accounts in a conversation, but only after an explicit yes.** Names, then emails, then each person's role, manager and department, then a summary with **Edit** and **Remove**; nothing is sent until **Yes, create and email**. Each account goes through the same `POST /users` as the People page; real admins only | Onboarding the instructors one wizard at a time is slow, and pasting a list is how people actually have the data. The confirmation step and the reuse of the server endpoint mean Puppy adds no new power: validation, password policy, the public demo guard and the audit log all still apply | It's rules, not language understanding: input has to be names and emails in the same order. Up to 25 people per batch |
| **The shared public demo admin can't be anyone's manager** (server rule and Puppy's picker) | Its password is published, so any visitor could act as that manager: approve the person's hours, read their profile, message them | None noted: real admins and managers are always available |
| **Skill matching stays "at least one required skill".** Auto-routing only gives a milestone that lists skills to someone with at least one of them; among those, the most matching skills wins, then the fewest open milestones, then the name | Requiring every skill would leave most milestones unroutable with a small team, and the manager can still assign by hand. Ranking by matched skills still prefers the best fit | Someone with one of three skills can be routed to a milestone they can only partly do; they can kick it back with a reason |
| **Push and pull projects, and completion routing skips pull projects.** In push mode (the default) the manager assigns work and *Completed* auto-routes freed people to the next ready milestone; in pull mode the team claims ready work themselves, so completion routing does nothing there ([`rules/routing.py`](../../backend/v1/app/rules/routing.py) `ready_for_routing`) | Auto-assigning in a pull project would take the choice away from the team and race their claims for the same milestone. Support routing on *Ready for review* still applies in both modes | A ready milestone in a pull project waits until someone claims it; it's listed under **Milestones you can claim** on the team's My week until then |
| **Puppy and smart insights are rules, not AI.** Insights are pure server-side rules; Puppy and the palette's phrases run in the browser on data the user already sees | The Lambda has no internet route, so no AI service is reachable; rules are predictable, testable and explainable ("Puppy follows rules from your data — no AI service involved") | No free-form understanding: questions outside the rule list get a fixed answer |
| **EmailJS browser relay for email** (welcome and reset emails, "Email this report") | The only way to send email from the live site without changing the shared infrastructure; see [Email on the live site](#email-on-the-live-site-a-browser-relay-2026-10-14) | The EmailJS public key ships in the browser; forgotten-password codes are never relayed |
| **SES stays off: blocked by IAM as well as the network.** The workshop Lambda uses the platform's pre-made role (`create_role = false` in `infra/lambda.tf`), which has no SES permission, and its VPC has no route to SES; participants can't change either | Recorded so nobody "fixes" email by retrying SES. The server fails fast (one try, short timeouts, 10-minute cooldown) and the relay takes over | Server-side email waits for the instructors: an SES VPC interface endpoint plus `ses:SendEmail` on the role |

## Email on the live site: a browser relay (2026-10-14)

- **Problem:** the Lambda runs in the VPC's "public" subnets, but AWS never gives a Lambda's network interface a public IP. It has **no internet route at all**, so SES and every third-party email API time out from the server.
- **Interim fix, no infrastructure change:** when the server reports `email_sent: false` for a new account or an admin password reset, the admin's browser sends the email through one fixed **EmailJS** template ([`frontend/src/lib/emailRelay.js`](../../frontend/src/lib/emailRelay.js)). If that also fails, or isn't configured, the show-once dialog appears as before.
- **Not relayed:** forgotten-password codes. The code would pass through the requester's own browser, which defeats it, so that flow still says "ask an admin".
- **Trade-off:** the EmailJS public key ships in the browser. EmailJS's free plan doesn't allow restricting it to this site's domain (that's a paid feature), so anyone who reads it could trigger this one fixed template to an address of their choosing. Two limits apply: the free plan's 200 emails a month, and server-side use is turned off. That's acceptable for the workshop demo; for production, upgrade to restrict the domain or use the SES endpoint below.
- **Proper fix (needs the instructors):** an SES SMTP VPC interface endpoint (`com.amazonaws.us-east-2.email-smtp`), with the backend sending through the standard library's `smtplib`. That also restores forgotten-password emails.

## Findings from the final deploy (2026-10-13)

### Deep links returned 403

- **What happened:** after the frontend went live, opening `/login` or refreshing any page returned S3's XML `AccessDenied`.
- **Cause:** the bucket is private, behind CloudFront Origin Access Control, so S3 answers a missing key with `403`. The distribution only maps `404` to `index.html`.
- **What we did:** added a CloudFront Function (`spa_routes`) on the default S3 behaviour. It rewrites any path without a file extension to `/index.html`. The owner chose this over mapping `403` (which would also have rewritten real API `403`s into HTML) and over hash URLs.
- **Related:** CloudFront's `404 → index.html` mapping also applies to API 404s. The API client therefore treats a non-JSON response as `404 NOT_FOUND`, and a top-level error boundary catches any screen that still crashes.

## Findings from the first cloud deploy (2026-10-13)

### SES email isn't reachable from the Lambda

- **What happened:** creating a user on the live site tried to send the welcome email through AWS SES. The connection timed out (`Connect timeout on endpoint URL: "https://email.us-east-2.amazonaws.com/"`), and the default AWS retries made the request take **95 seconds**.
- **Cause:** the workshop's Lambda runs inside a VPC with no route to the internet or to SES. This is a network limit of the provided infrastructure, not a permissions problem.
- **What we did:**
  - The email client now uses a short connect timeout (3 seconds then, 1 second today), a 5-second read timeout and no retries.
  - After one failure, SES is skipped for 10 minutes, so later requests fall back instantly.
  - When an email can't be sent, the admin sees the temporary password once, with a copy button, to pass on directly.
- **What's still limited:** on the live site, forgotten-password codes can't be emailed. Users have to ask an admin to reset their password. Local development writes every email to `backend/v1/.outbox/`.
- **Real fix:** give the VPC a route to SES (an SES VPC interface endpoint, or a NAT gateway). This needs the instructors' approval, because it changes the shared infrastructure.

### Login was slow on a 128 MB Lambda

- **What happened:** each password hash (PBKDF2-SHA256, 600,000 iterations) took about **4.4 seconds**, so login took about 4.6 seconds.
- **Cause:** AWS gives a Lambda CPU in proportion to its memory. At 128 MB it gets a small fraction of one CPU.
- **What we did:** raised `memory_size` from 128 to 1024 MB in `infra/lambda.tf`. Login now takes **about 0.75 seconds warm** (about 1.6 seconds on a cold start), with the full 600,000 iterations kept. The owner chose this over weakening the hash.
- **Cost:** higher price per millisecond, but each request finishes faster. Negligible at workshop scale.
- **Cold start:** about 0.45 seconds to initialize the Lambda.

### Demo admin logins

The live site has no guessable admin login. The admin demo accounts are `admin.demo2`, `admin.demo3` and `admin.demo4`, created with the `create_admins` operation: an IAM-only Lambda invoke (like `migrate` and `seed`) that the public Function URL can't reach. Each gets a random strong password, returned only to the operator and held privately by the owner. `manager.demo` and `employee.demo` keep `Demo123!` for graders.
